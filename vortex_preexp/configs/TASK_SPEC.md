# VortexHash｜MTT S4000 48GB 预实验执行任务书

**执行对象：Codex**

**研究阶段：** 可行性预实验，不是完整论文实验。

**硬件：** 单张摩尔线程 **MTT S4000 48GB**（MUSA 平台）；CPU/内存按服务器现状使用。**不是 NVIDIA/CUDA 环境。**

**GPU 预算：** 目标约 **25–30 GPU·h**，默认硬上限 **36 GPU·h**（按本卡实际占用的累计墙钟时间统计；环境下载/离线数据处理另记）。

这不是 RTX 5080 的等效 GPU 小时；必须先测 MUSA 环境的真实吞吐，再确定每个模型的统一 token 预算。到达上限结束当前最小实验单元并保存结果；不自动租卡、扩卡或无界增加任务。

**输出：** 可复现代码、结果数据和有证据的 GO / MODIFY / STOP 判断。

**平台边界：** RTX 5080 版任务书的核心假设与对照不变；只改变实验硬件、设备兼容适配、计时方法和有限卡时预算。不得把 MUSA 计时当作 NVIDIA 性能，或把 simulated FP4 当作原生硬件加速。

## 0. 先准确理解研究问题

目标不是证明“置换可以表示相对位置”（这是已知数学性质），也不是重复展示 61,616,126 的联合周期，更不是给整数余弦模板拟合出漂亮曲线。

要验证：

**在保持可用语言建模能力的前提下，带符号的离散相对位置算子是否在低比特 Q/K 上，比公平的 RoPE 实现有实质优势？该优势是否来自精确置换，而不是换频谱、差基线或虚假的 GPU 计时？**

三个核心研究问题：

- **RQ1——量化机制：** VortexHash 的精确置换能否在相同 Q/K 位宽和量化尺度预算下，降低注意力 logit / 输出误差？尤其是每 head 一尺度与每 16 维一尺度的差别。
- **RQ2——表达与学习：** 11/13/17/19/23/29 六个反周期环（112 维）+16 个不变维度，是否让 128 维 head 的局部、长程依赖学习明显弱于 RoPE？
- **RQ3——工程现实：** 在 MTT S4000 的 MUSA/PyTorch 路径上，这个算子能否以可接受的实现开销运行？低比特分组缩放会不会使“精确”性质失效？（MUSA 测时结果不直接代表 NVIDIA 上的速度。）

**原始方案固定：** 每 head 128 维；环长 `[11,13,17,19,23,29]`，合计 112 维；末尾 16 维保持不变。

定义：

\[
G_L(x)=(-x_{L-1},x_0,\ldots,x_{L-2})
\]

\[
T(p)=\bigoplus G_L^p\oplus I_{16}
\]

首先不要私自将其改成动态哈希、普通滚动位置、分桶位置或另一个模型。

原文的固定整数模板属于**路线 B**，当前主实验只研究 **路线 A：直接对 Q/K 施加 \(T(p)\)**；模板只做数学诊断，不要把二者混为同一模型。

## 1. 执行原则

1. **先做最有判别力的测试，不写大框架。** 最多保留必要的 reference 实现、训练脚本、评测与微基准。
2. **不升级 GPU 驱动、不重装系统、不自动租卡、不新增外部机器。** 优先使用镜像中**已经可用**的 MUSA SDK、`torch_musa` 和对应 PyTorch；可在隔离 Python 环境中补充依赖，但不要自行替换系统 MUSA 驱动/SDK。设备应为 `musa`，不可默认使用 `cuda`/`sm_120`/CUDA 专用 FlashAttention/Triton kernel。`torchada` 可以作为经验证的兼容层，但不能让设备实际退回 CPU。
3. **不要把 fake-quant 伪称原生 INT4/FP4 kernel。** 首轮低比特采用可验证的模拟量化，再还原到 BF16/FP32 做 attention；只能据此判断数值和模型质量，不能据此宣称 4-bit 推理加速。
4. **先跑 MUSA 训练与算子吞吐 pilot**，确认算子在设备上执行，再在统一 token / optimizer step 预算下比较。不能因某方法收敛慢就给它更多 token。
5. 1 个随机种子做初筛；只有关键结果接近决策阈值时才增加第二种子。不要把预算花在十几个数据集、十几个超参、7B 模型或无关健壮性测试上。
6. 优先保证一对一可解释的因果比较；碰到不可控环境问题，记录、选择最小可行替代并继续。可以自主提出**最多 1 个明确可解释的修正版**，但必须先保留原设计完整结果。

### 1.1 MTT S4000 的执行适配

- **平台发现：** 运行 `musaInfo`（若命令可用）；记录 MTT S4000 48GB、驱动、MUSA SDK、`torch`、`torch_musa`、Python 版本。以 `torch.musa.is_available()` / 一次小矩阵 GPU 计算验证实际执行设备；不要仅根据包安装成功判断可用。

- **Attention 后端：** 优先测试 `torch.nn.functional.scaled_dot_product_attention` 在当前 MUSA 版本的前向/反向兼容性及实际吞吐；若不支持或运行有问题，使用**所有方法一致**的 eager/matmul+softmax causal attention。回退要在报告中记录；不能只给某个基线使用更快 kernel。
- **量化仍然先模拟：** S4000 官方列出的常用精度为 FP32/TF32/FP16/BF16/INT8，**不要预设原生 FP4/NVFP4 Tensor Core 或 NVIDIA 的每 16 值缩放路径存在**。`group16 INT4` 与 `FP4 E2M1` 都仅作为软件模拟的数值模型；不必为本轮研发原生 4-bit kernel。
- **性能测量：** 不要直接使用 `torch.cuda.Event`、CUDA graphs 或 Nsight CUDA 计时。优先采用当前 `torch_musa` 实际支持的 GPU events；否则使用 `time.perf_counter()` 包围同步的设备调用（前后 `torch.musa.synchronize()`，以实际 API 为准），多次 warm-up、重复取中位数/p95。统计设备时间时**禁止无意异步计时**。
- **编译优化：** `torch.compile`、Triton-MUSA 或 MUSA 自定义 kernel 都属于**可选项**。没有现成稳定支持就跳过，不能为了跑通编译器占满预算。不得调用 CUDA-only 扩展后把失败认作研究方法失败。
- **资源策略：** 48GB 显存仅用于适度提高 batch、避免 OOM 和保证对照公平；**本轮模型规模、任务、对照不自动膨胀**。先做 3–5 分钟 pilot，记录 tokens/s、显存与实际后端，然后为所有方法使用相同的数据 token 预算；训练时间可能和 5080 相差很大。
- **性能结论边界：** MUSA 后端的算子开销具有平台特性。P4 只回答“在这张 MTT 卡上代价是否可控”；若将来要声称 NVIDIA/原生 INT4/FP4 推理加速，需另做对应硬件验证。

## 2. 必须实现的核心对照

| 简称 | 位置编码 | 作用 |
|---|---|---|
| `rope_safe` | 标准 RoPE，正确的角度精度，正常一次量化流程 | 实用主基线，禁止故意使用 BF16 角度制造错误 |
| `vortex` | 本文六个带符号置换环 + 16 identity | 主方法 |
| `ring_plain` | 相同环长但没有跨界翻符号的循环置换 | 合成任务消融，判断反周期的附加价值 |
| `spectral_rope` | 与 `vortex` **完全同频谱**的正交旋转表示 | **最关键的机制对照**，隔离“换频率”与“换实现/量化坐标系” |

**`spectral_rope` 不需要额外训练一遍。**

每个环构造实正交基 \(U\)，使：

\[
P=URU^\top
\]

其中 \(R\) 为相应二维旋转块（奇数环可能有一维 \((-1)^p\) 模式）。

将训练好的 `vortex` 模型中每个 head 的 \(W_Q,W_K\) 离线改成：

\[
U^\top W_Q,\quad U^\top W_K
\]

运行时使用 \(R(p)\)。

在 FP32 下这两个模型对相同输入的注意力分数应在数值容差内一致。

**不要把它当作另一种改变频率、重新随机初始化的 RoPE。**

若转换后不等价，优先修复代码，再看量化结论。

注意：高精度下 `vortex` 和它的等谱旋转在适当换基后函数等价，但它与**标准 RoPE** 的频谱并不相同。三个比较需要同时存在。

## 3. P0：环境与数学正确性

**目标：1 GPU·h**

- 记录 GPU 型号、显存、驱动、MUSA SDK、`torch_musa`、PyTorch、Python、当前注意力后端，并完成 MUSA 实际设备计算、反向传播与短吞吐 pilot；不需要 SM/CUDA 信息。
- 参考实现：整数下对正负 `p` 的带符号移位，含 \(G_L^L=-I\)、\(G_L^{2L}=I\)、正交性、\(T(m)^TT(n)=T(n-m)\)、同相对距离的整数点积分数。
- 批量实现：预计算每个位置、每个维度的 source index 和 sign；对 `[B,S,H,128]` 的 Q/K 使用一次 gather/重排，不允许在 token/head 循环里反复调用 Python `torch.roll`。
- 在小矩阵上构造等谱 \(U,R\)，随机 Q/K 验证 \(P=URU^T\) 和经过投影映射后的 FP32 logits 一致。建议最大绝对差与相对差均记录，通常应在 `1e-4` 量级以内（以实际 FP32 矩阵规模判断）。
- 独立计算 `tr(T(Δ))/128`，至少对 `Δ=0,1,2,11,58,1333,1334,1335,14674,25346` 出表；画 `Δ=0..2048` 的相关性/特征谱图。特别检查单环最长非零周期仅 58、联合周期虽大仍有强部分重合。这是诊断，不是模型性能的替代证据。

**通过标准：** 数学不变量、实现方向、等谱 FP32 映射全部成立，才进行 P1。

## 4. P1：最关键的低比特机制试验

**目标：2 GPU·h**

使用三类输入：

1. 各向同性随机 Q/K；
2. 重尾或含离群值分布；
3. 后续从训练模型采集的真实 Q/K（模型完成后补测，不为此阻塞 P1）。

统一维度、随机种子、样本数与量化预算。

### 必须比较

- `FP32/BF16` 高精度分数基准；
- `rope_safe`：**先正确旋转，再量化一次**，禁止与双重量化的差实现比较；
- `vortex`：先量化再置换、先置换再量化，两条路径分别测；
- `spectral_rope`：由同一批 `vortex` Q/K 经离线等谱坐标变换得到，正确旋转后只量化一次。

### 量化情形

不要全组合爆炸。

1. **对称 INT4** `[-7,7]`，每个 token/head 共享一个尺度：是精确交换律的正例；
2. 同样 INT4、**每连续 16 维一尺度**：是分组尺度可能破坏交换律的关键反例；
3. **FP4 E2M1 + 每 16 维尺度的模拟**（若实现简单），明确为 simulated FP4；真实 NVFP4 训练/推理内核不列入本次必做；
4. 对 Q+K 都量化，并额外做一次仅 K 量化（KV-cache 相关性）。

### 观测指标

- `Q(Px)` 与 `P Q(x)` 的编码码值一致率、反量化数值差异；注意 INT4 不使用不可精确取负的 `-8`；
- 固定内容 Q/K、相对距离 Δ，改变绝对偏移 `p∈{0,256,4096,65536,1000000}` 时的分数漂移；可用 64 位参考角度，但不得把不合理的 RoPE 精度损失算成主要贡献；
- 对 FP32 参考 attention logit 的 MAE、NRMSE、softmax KL、top-1 变化率，分段汇总 `Δ∈{1,2,8,32,128,512,1333,1334,1335}`；
- 每 16 维尺度是否会穿越环边界：若不保持值，直接在报告标明“不具备原生 block-scale 精确性”，不要把 per-head 结果外推到 NVFP4。

**核心问题：**

与等谱旋转相比，精确置换到底减少了多少**有意义的 attention 误差**？与正确实现的标准 RoPE 比，是否仍有优势？

若只是数学上误差为零，但下游 attention 没差别，不要报喜。

## 5. P2：极小模型合成任务

**目标：8 GPU·h**

固定训练骨架：decoder-only Transformer，head_dim=128，d_model=512，4 heads，优先 2–4 layers，普通 causal attention。

不要混入长上下文技巧、外部 memory 或复杂新结构。

### 任务 A：局部复制 / 相对位置选择

输入大量随机符号，查询时要求输出明确相对位置上的符号（控制查询偏移和位置分布），测模型是否能高精度利用临近位置与指定距离。

随机标签与 token，不能让内容统计泄漏答案。

### 任务 B：关联检索 / 重复干扰

给若干随机 `key→value` 对，在末端按 key 提问，返回对应 value。

加入相同 token 模式、不同相对位置的干扰项。

训练序列长度优先 256 / 512；评估 256、512、1024、2048。

对 1333、1334、1335 等距离设计完全匹配难度的控制样本，检查异常撞峰，但不要仅凭这几个点下结论。

### 模型对照

- `rope_safe`
- `vortex`
- `ring_plain`

固定参数量、训练数据顺序、tokens、优化器、学习率、精度、批量有效大小。

首先 1 seed，不做大范围调参。

合成数据和评测数据以固定生成器 seed 产生，测试样本在训练过程中不可见。

### 输出要求

输出：

- 训练曲线；
- loss/accuracy；
- 按长度与间距的准确率；
- 相对标准 RoPE 的差值。

训练结束对同一 checkpoint 加入 `Q/K INT4 fake-quant`（每 head 和 group16）比较精度跌幅，不额外训练一套量化模型。

可以把 Vortex checkpoint 映射为等谱旋转再做 PTQ，测试其预测一致性。

**决定点：**

如果原始 `vortex` 在两种任务的 BF16 下明显无法学好，而标准 RoPE 可学，且低比特没有足以抵消的收益，就先停止，不要立刻扩大语言模型。

若问题主要发生在 1334 附近，保留结果并明确是频谱/重合弱点。

## 6. P3：最小真实文本试验

**目标：12 GPU·h，有信号才执行**

在 P2 没有明显失败、P1 显示非平凡低比特优势时执行。

### 数据集

单一固定数据集：优先 **WikiText-103 raw**。

训练集按固定顺序取若干 token，验证集固定且与训练无泄漏。

训练统一的约 16k tokenizer（只在训练文本上拟合），记录版本。

若网络或数据不可用，可换公开且可稳定下载的真实英文文本子集，但必须记录变更理由、来源、tokenizer 和切分。

**不能仅用 TinyStories 来代表真实语言建模能力。**

### 模型配置

**模型约 27M 参数：**

- decoder-only；
- 6 layers；
- d_model=512；
- 4 heads；
- head_dim=128；
- FFN 约 4×hidden；
- tie embedding；
- vocab 约 16k；
- context=512；
- AdamW；
- BF16。

训练两条主线：

- `rope_safe` BF16；
- `vortex` BF16。

对相同训练数据、相同初始随机源、相同 token 与 scheduler 预算训练。

保持 batch、优化器等相同。

训练前测一小段吞吐，选择**两条训练都能在 P3 预留预算内完成的共同 token 预算**。

目标每个模型约 50M tokens，吞吐不足则先报告可实现数量。

若每条少于约 20M tokens，则只能算 smoke test，不得将小幅 NLL 差当作有效结论。

训练数据固定、不按模型动态调整。

保存 10M/25M/最终 checkpoints（条件不允许可减到中期+最终）。

### 推理侧 PTQ

在**同一批 BF16 训练 checkpoint** 上做推理侧 PTQ，不需要训练额外 QAT 模型：

- 原始 BF16 NLL / perplexity；
- `Q+K INT4 fake-quant`（per-head 与 group16）；
- `K-only INT4 fake-quant`（至少 per-head）；
- 将 `vortex` checkpoint 离线映射为 `spectral_rope`，验证高精度输出相同，再对其做对应 PTQ；
- 可选模拟 FP4 E2M1（前提是不侵占主实验预算）。

统一记录：

- 绝对 validation NLL；
- `quant_penalty=NLL(quantized)-NLL(BF16)`；
- 长度分桶和局部依赖样本表现；
- 显存峰值；
- 训练 tokens/s。

**绝对 NLL 与量化损失增量必须同时报告。**

不允许只展示 Vortex 的降幅更小而忽略其 BF16 原始质量更差。

### 本轮不强求的内容

- 1B/7B；
- 全部量化格式；
- QAT；
- 多个公开 benchmark；
- 微调已有 RoPE 大模型。

除非 PTQ 全面崩溃但前两阶段特别有价值，且还有预算，才可以试相同计算预算的极短 QAT；要显式区分 PTQ 和 QAT。

## 7. P4：有限性能测试

**目标：3 GPU·h**

在 **MUSA 设备上**充分 warm-up、同步和重复采样，以可用的 GPU events 或同步的 wall-clock 计时。

比较在相同 `[B,S,H,128]` 下：

1. `rope_safe` 位置操作与 `vortex` 预计算索引的批量 gather / 符号处理；
2. 接入相同且已确认可用的 PyTorch SDPA 后端（不支持则统一 eager attention）的整体 prefill 和单步 decode 路径；
3. 若现成 `torch.compile`/Triton-MUSA 已可用且明显降低开销，可补一版；否则跳过，不要为微弱速度差开发完整自定义 attention kernel。

### 测试范围

至少覆盖：

- Prefill：`S={128,512,2048}`
- Decode：`S={512,2048}`

选取能装入 48GB 的合理 batch，**但公平比较时保持各方法 batch 一致**。

记录：

- Median latency；
- P95 latency；
- 显存峰值；
- attention backend；
- GPU 实际执行时间。

**必须明确这是 MUSA BF16/FP16 或 fake-quant 性能，不是原生 4-bit attention 加速，也不是 RTX 5080 性能。**

若 gather 版本远慢于 RoPE，应分析是算法固有的数据重排代价，还是 Python/未融合实现问题。

不得直接用未经优化代码宣称方法失败或成功。

### GO / MODIFY / STOP

这些是科研决策参考，不是统计学判决界线。

**GO——继续：**

- P1 对等谱旋转有明确低比特 logit / attention 误差收益；
- P2 的 BF16 能稳定学好关键任务且 INT4 掉点更小；

**MODIFY——修改方向：**

- P1 的 per-head 精确性成立，但 group16 失效；
- 或者近邻学习、1334 距离碰撞使 P2 明显退化。

提出**一个**有理论动机的修正版（如组尺度一致的环布局），单独列为后续工作，不要覆盖原始结果。

**STOP——停止：**

- 等谱校验完成后，在合理低比特设置下没有实质误差优势；
- 而且合成任务或文本 BF16 质量显著劣于 RoPE。

直接汇报为什么不值得继续。

尤其不能靠劣化 RoPE 的实现制造胜利。

可把“等谱误差降低 20% 左右、量化任务掉点减少数个百分点、文本 NLL 差异超过运行噪声”当作希望看到的信号，但必须同时给原始数据，不能把事前阈值当成论文结论。

  reports/DECISION.md           # GO / MODIFY / STOP + 后续建议

每个 run 记录：

- 代码提交 hash（若有仓库）；

### PREEXP_REPORT.md 的结构

严格按以下组织：

**研究问题 → 方法与基线 → 实验设置 → 核心结果表与曲线 → 是否证明了什么 → 未证明什么 → 下一步建议**

1. 等谱变换的 FP32 等价性检查，以及 `Vortex` / 等谱旋转 / 标准 RoPE 的 INT4 attention 误差对照；
2. per-head 与 group16 缩放时 `Q(Px)=P Q(x)` 的成立/失效证据；
3. 合成任务随长度与距离变化的准确率；
4. 若 P3 执行，文本绝对 NLL 与 quantization penalty；若未执行，说明停止的实验事实。

性能单独标注环境与计时边界。

最后必须给出一句话判断：

**“这个方向继续做论文，行 / 需要改 / 不行。”**

并指出最强证据和最致命问题。
